# 03 · 缺陷修复单（给开发，可直接执行）

> **用途**：测试同学每发现一个缺陷，都在这里留一张"可执行工单"——开发拿到就能复现、定位、修改、验收。
> **状态口径**：`⏳ 待修` / `🔧 修复中` / `✅ 已修（附验证）` / `🚫 产品决策（不修）`
> **验收方式**：对应 xfail 用例从 `XFAIL` 变 `XPASS` 即视为修复通过（机器验证，不靠口头确认）。

## 使用说明

1. 复现：`curl` 命令直接粘到终端（本地 `python sut/app.py` 用 seed 数据即可）
2. 定位：已给出 `文件:行号` 与代码片段
3. 修复：按"修复建议"改，改完 `python -m pytest` 看对应用例是否转 XPASS
4. 回归：该用例会长期保留，防止同一缺陷复发

## D19 · 云端 500 被裸 `except` 吞掉，伪装成 404

| 项 | 内容 |
|---|---|
| 严重级 | P2 |
| 影响 | 云端故障与"图片不存在"返回同一响应，前端无法重试、监控无法告警 |
| 状态 | ⏳ 待修 |

**复现**（假云端置 500 模式）

```bash
# tools/fake_cloud.py 起来后
curl -X POST http://127.0.0.1:<fake云端口>/__mode -d '{"mode":"objects_500"}' -H 'Content-Type: application/json'
curl -i "http://127.0.0.1:8123/api/thumb/11111111-1111-4111-8111-111111111111"
# → 404 + 空 body（应 502/503 + 错误体）
```

**根因**

```python
# app.py:781-789  get_thumbnail
try:
    resp = requests.get(cloud_url, timeout=10, verify=False)
    if resp.status_code == 200:
        return Response(resp.content, ...)
except:            # ← 裸 except 吞掉一切（含 timeout / 连接失败 / 5xx）
    pass
return '', 404     # ← 与"图片不存在"同响应
```

**修复建议**

```python
try:
    resp = requests.get(cloud_url, timeout=10)
except requests.Timeout:
    return jsonify({'error': 'cloud_timeout'}), 504
except requests.RequestException:
    return jsonify({'error': 'cloud_unavailable'}), 502
if resp.status_code == 404:
    return jsonify({'error': 'image_not_found'}), 404
if resp.status_code >= 500:
    return jsonify({'error': 'cloud_error', 'upstream': resp.status_code}), 502
return Response(resp.content, content_type=resp.headers.get('Content-Type', 'image/jpeg'))
```

**验收**：`tests/test_cloud_mock.py::test_thumb_cloud_500_should_not_mask_error` → XPASS

```python
csv_files = ['画作信息_男.csv', '画作信息_女.csv', '画作信息_有男有女.csv', '画作信息_点景人物.csv']
```

## D04 · 全站 10 处 `verify=False` 关闭 TLS 校验

| 项 | 内容 |
|---|---|
| 严重级 | P2（安全）|
| 位置 | `app.py` 第 50、196、230、264、290、320、388、783、804、983 行 |

**问题**：关闭证书校验后，中间人可替换云端图片内容；且 `verify=False` 在较新 requests 会告警。
**修复建议**：去掉 `verify=False`；若内网自签证书确实需要，改为挂载公司 CA（`verify='/path/ca.pem'`），而不是全局关闭。

## D08 · `/api/download` 无上限、逐张串行下载、不可中断

| 项 | 内容 |
|---|---|
| 严重级 | P2（性能/可用性）|
| 位置 | `app.py` `download_images()`（约 883 行起）|

**问题**：筛选结果不设上限，逐张 `requests.get` 串行拉图；一个请求可能跑几分钟，客户端断开也无法中止，容易拖垮 worker。
**修复建议**：① 限制单次打包数量（如 100 张）并在响应头告知；② 用线程池并发拉取（8 并发）；③ 加总超时预算，超时返回已成功部分 + 缺失清单。

## D09 · 错误响应格式不统一

| 项 | 内容 |
|---|---|
| 严重级 | P3（契约一致性）|
| 位置 | 全站 |

**现状**：有的返回空 body（`''` + 404）、有的返回 `jsonify({'error': ...})`、有的返回 HTML 500 页。
**修复建议**：统一错误体 `{"error": "<code>", "message": "..."}`，并用 `@app.errorhandler` 兜住 404/500。

## D10 · 4 处裸 `except:`

|---|---|
| 严重级 | P2（可观测性）|

## D12 · `/api/public_copyright_ids` 每次重读文件 + `set` 顺序不稳定

| 项 | 内容 |
|---|---|
| 严重级 | P3（性能/幂等）|
| 位置 | `app.py:554-570` |

```python
with open(ids_file, 'r', encoding='utf-8') as f:   # 每个请求都读一次文件
    data = json.load(f)
...
return jsonify(list(set(all_ids)))                  # set → list，顺序不保证稳定
```

## D14 · `/api/scroll` 拼接无超时预算

| 项 | 内容 |
|---|---|
| 严重级 | P2（长尾延迟）|
| 位置 | `app.py` `build_scroll_image()`（瓦片循环）|

**问题**：每张瓦片 `timeout=15`，N 张瓦片串行请求，最坏情况 15s × N；请求会被网关/浏览器先断，但服务端仍在跑（浪费资源）。
**修复建议**：设总预算（如 20s），超预算即返回已拼部分 + 缺失信息；或改用并发拉取。

## D16 · 启动全量加载 549MB JSON

| 项 | 内容 |
|---|---|
| 严重级 | P3（启动/内存）|
| 位置 | `app.py:65-75`（`pose_results_all.json` 等）|

**问题**：进程启动把 5 个 JSON 全读进内存（生产环境约 549MB），冷启动慢、内存占用高，多 worker 时内存翻倍。
**修复建议**：改按需加载（首次访问某 uuid 时才读该条）或用 SQLite/LevelDB 预建索引；短期可把大文件转成 `jsonl` 流式加载。
