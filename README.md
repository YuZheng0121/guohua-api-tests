# 国画分析 WebUI 接口自动化测试

[![api-tests](https://github.com/YuZheng0121/guohua-api-tests/actions/workflows/api-test.yml/badge.svg)](https://github.com/YuZheng0121/guohua-api-tests/actions/workflows/api-test.yml)

对一个真实 Flask 项目的接口层与页面层做自动化测试与缺陷挖掘：**21 个路由、55 条用例、发现 15 个已复现缺陷**，CI 双 Python 版本矩阵 + 独立 E2E job，全部通过。

被测系统（SUT）是一个真实的课题组内部 WebUI（992 行，中国绘画关键点/检测结果可视化），脱敏副本见 [`sut/app.py`](sut/app.py)。测试过程中对 SUT 只做了 3 处**可测性改造**（数据目录 / CSV 目录 / 端口支持环境变量），业务逻辑一行没改——缺陷保持原样，因为它才是测试对象。

## 快速开始

```bash
pip install -r requirements.txt
python -m pytest -qrx
```

预期结果：`26 passed, 9 deselected, 14 xfailed, 5 xpassed in ~3s`

（`9 deselected` 是被 `-m "not e2e"` 排除的页面级 E2E 用例，属正常。）

```bash
python -m playwright install chromium
python -m pytest -q -m e2e -rx
```

预期结果：`7 passed, 2 xfailed`。

> ⚠️ Windows `cmd.exe` 不把 `#` 当注释符。复制命令时不要连同后面的说明一起复制，否则 `#` 会被当成参数传给程序。

`xfailed` 不是失败，而是**已知未修复缺陷**：用例断言的是"正确契约"，当前实现不满足，因此预期失败；缺陷修复后它们会自动变成 XPASS，CI 保持绿色同时不掩盖问题。

生成 HTML 报告：

```bash
python -m pytest --html=test-output/report.html --self-contained-html
```

## 修复记录（2026-11-08）

已修复 4 个影响最直接的缺陷，**验证标准统一是"对应缺陷用例由 XFAIL 转为 XPASS"**：

| 缺陷 | 修复内容 | 验证结果 |
|---|---|---|
| **D11** P1 | `open()` 增加 `encoding='utf-8'`（3 处），消除中文 Windows 下 GBK 解码失败 | 2 条用例 XPASS，`/api/images_count` 恢复 200 |
| **D17** P2 | 删除 `images.html` 中对未定义函数 `loadFilterOptions()` 的调用 | 页面不再抛 ReferenceError |
| **D18** P2 | 抽出 `fetchJson()`，先校验 `res.ok` 再解析，错误信息可读 | 页面加载无未捕获异常 |

回归结果：`26 passed, 14 xfailed, 5 xpassed`（接口）＋ `7 passed, 2 xpassed`（E2E）。

剩余 5 个已复现缺陷（D01 端口提示、D05 资源不存在返回 200、D06 分页负索引、D07 `per_page` 无上限、D13 标签空间混用）保留为**已知问题**，对应 xfail 用例继续作为回归基线；它们都需要产品决策或跨端改造，不适合在测试仓库里单方面修改。

> 修复通过 `tools/bootstrap_fixtures.py` 的 `apply_fixes()` 固化：重新生成 SUT 副本时会重新打补丁，`assert` 保证锚点不漂移。

## 设计上值得说的几点

1. **测试数据与生产数据分离**：真实数据 549MB（`pose_results_all.json` 366MB），直接用于测试会让 CI 无法运行。改用 3 条定长记录的 seed 数据集，启动从分钟级降到秒级；代价是 SUT 需要支持 `GUOHUA_DATA_DIR` 注入——这就是"为可测性改造被测系统"。
2. **xfail 表达契约，而不是迁就现状**：缺陷用例断言"应该 404"，而不是"当前返回 200 所以断言 200"。修复后自动 XPASS，缺陷与用例同生共死。
3. **就绪探测用轮询而非 sleep**：避免固定等待造成的 flaky 和慢测试。
4. **踩过一个典型坑并修掉**：SUT 的 stdout 最初用 `subprocess.PIPE`，500 响应的 traceback 把管道缓冲区写满后，被测进程阻塞在 `write` 上，表现为"所有请求无响应"的假死。改为重定向到 `test-output/sut.log` 后解决，并顺带获得了可追溯的服务端日志。
5. **接口测试 + E2E 互补**：D17/D18 两个缺陷接口层完全看不见——接口都是 200，但页面初始化抛异常、筛选计数永久为 0。反过来 E2E 也发现不了 D06/D07 这类参数边界问题。两层缺一不可。
6. **修缺陷要看调用方**：前端第 637 行依赖 `api/images?per_page=20000` 拉全量，说明 D07（无上限）已经被调用方依赖。如果只给接口加 500 上限，页面会静默少数据而不报错——所以 D07 必须连带前端分页一起改。
7. **CI 自包含**：`sut/` 目录随仓库提交，CI 不需要原项目即可运行。

## 真实数据验证（2026-11-15）

为了证明"缺陷不是 seed 人造的"，用真实数据集做了两组实验：

| 数据集 | 规模 | 启动耗时 | 进程内存 | 结果 |
|---|---|---|---|---|
| **全量真实数据** | 549MB / 18984 条 | **> 9 秒未就绪** | 9 秒涨到 **1.5GB**，系统可用内存降到 0.25GB | ❌ 本机（可用 1.6GB）直接放弃——这就是"真实数据进不了 CI"的内存原因 |
| **真实抽样集** | 9.6MB / 300 条真实记录 + 真实 CSV | **2.1 秒** | **79MB** | ✅ 8 个核心接口全 200 |
| seed 集 | 0.3MB / 3 条合成 | ~2 秒 | ~70MB | ✅ CI 日常回归 |

**真实抽样集下验证到的内容**：

- `total = 597`（真实数据多源合并：detection 300 + CIT-only 297），`copyright_count = 156 ≤ total` → **D24 的修复在真实数据下同样成立**
- `category_count = {女:34, 有男有女:44, 点景人物:96, 男:126}`，`filter_options` 仍出现伪分类 `CIT检测` → **D23 在真实数据下同样存在**
- 真实朝代 10 个：五代十国 / 元代 / 先秦 / 宋代 / 明代 / 未知 / 清代 / 近现代 / 隋唐 / 魏晋南北朝
- 真实 uuid 查详情：`/api/image/<真实uuid>` → 200，**4ms**
- **D06/D07 在真实数据下复现**：`page=0` → items=0 但 total=597；`page=-1&per_page=1` → 返回 1 条（尾部数据）；`per_page=1e8` → 返回全部 597 条

**结论**：缺陷不是合成数据的产物；同时验证了"全量真实数据只能按需跑，不能进 CI"这一取舍。

### 远程全量实测（128 核 / 1 TB 内存 / A100-80GB 服务器，2026-11-16）

真实数据已在课题组服务器上（`pose_results_all.json` 350 MB + `merged_results.json` 74 MB），
上传被测系统后启动全量服务。

> **注意口径**：这里跑的是**契约级检查（8 个接口 + 3 组分页边界）**，**不是**那 55 条 pytest 套件 ——
> 套件断言绑定 3 条 seed 的具体值（如 `total == 3`），在真实数据下必然失败。
> 真实数据验证需要"不写死值"的断言；目前以脚本形式执行，尚未固化为 pytest 用例（见「局限与后续」）。

**实测结果**：

| 指标 | 结果 |
|---|---|
| 真实全量记录数 | **18984 条**（女 2684 / 男 8164 / 有男有女 2427 / 点景人物 5709）|
| 冷启动到就绪 | **13.4 s** |
| 内存峰值（VmHWM）| **1.9 GB**（常驻 RSS 1.46 GB）—— 与"94 KB/条 × 18984 ≈ 1.75 GB"外推吻合 |
| `/api/images?per_page=5` | 200 · 52 ms · 1.0 KB |
| `/api/images_count` | 200 · 31 ms · 150 B |
| `/api/stats` | 200 · **720 ms** · 3.5 KB（全量遍历，最慢接口）|
| `/api/filter?category=女` | 200 · 47 ms · **471 KB** |
| `/api/shinu52` | 200 · 104 ms · 1.3 MB |
| `per_page=1e8`（D07）| 200 · 101 ms · **3.6 MB**（一次拉全量）|
| `page=0`（D06）| 200 · items=0 但 total=18984 |
| `page=-1&per_page=1`（D06）| 200 · 返回 1 条（尾部数据）|

**三条结论**：
1. 全量真实数据在 1 TB 内存机器上**可正常启动与响应**（13.4 s / 1.9 GB），而本机（1.6 GB 可用）跑不动 —— 这正是"真实数据不进 CI，但可按需在大内存机器上验证"的实证；
2. **D06 / D07 在真实全量数据下同样复现**，缺陷不是合成数据造出来的；
3. 真实数据下最值得关注的是 `/api/stats`（720 ms）与 `per_page=1e8`（3.6 MB 响应）。

> 远程执行目录：`/opt/data/private/qa-guohua-tests/`（README + sut/ + reports/，内含本次结果与日志）

### 规模曲线（同一份真实数据，按条数抽不同规模）

| 记录数 | 数据体积 | 启动耗时 | 进程 RSS | `/api/images?per_page=5` | `/api/stats`（全量遍历）|
|---|---|---|---|---|---|
| 300 | 9.6 MB | 1.55 s | 80 MB | 23 ms | 14 ms |
| 1500 | 39 MB | 1.55 s | 193 MB | 24 ms | 62 ms |
| 3000 | 76.5 MB | 3.61 s | 341 MB | 28 ms | 94 ms |
| 6000 | 145.5 MB | 4.02 s | 602 MB | 186 ms | 195 ms |
| **18984（全量）** | **549 MB** | **> 9 s 未就绪** | **1.5 GB+（中止）** | — | — |

**量化结论**：
- **内存按约 94 KB/条线性增长** → 外推 18984 条约需 **1.75 GB**，与实测"9 秒涨到 1.5 GB 后撑不住"吻合
- **`/api/stats` 延迟随数据量线性增长**（14 → 62 → 94 → 195 ms），因为它每次全量遍历
- 启动耗时在 3000 条后明显跳变（1.55 → 3.61 s），说明大 JSON 解析有拐点
- 这组数字直接支撑了取舍：**CI 用 3 条 seed（秒级、几十 MB），真实规模只能按需在大内存机器上跑**

> 抽样方法：只读每个大 JSON 的前 12MB，用 `json.JSONDecoder.raw_decode` 逐个解析数组元素取前 300 条，
> 保留真实 uuid / 字段 / 嵌套结构，把 549MB 压到 9.6MB（脚本放在仓库外，属一次性验证工具）。

## 局限与后续

**已补齐（2026-11-14 ~ 11-16）**
- 云端依赖已用**本地假云端**覆盖：`tests/test_cloud_mock.py` 10 条用例，覆盖成功 / 404 / 500 / 部分瓦片失败（含长卷拼接），由此抓出 D19~D22 四条"故障被伪装成正常响应"的缺陷。
- 已有性能基线：`tools/bench.py`（单请求约 8 ms、1/10/20 并发 RPS 101/29.5/12.2）与**全量真实数据实测**（18984 条 / 13.4 s 启动 / 1.9 GB 内存 / `/api/stats` 720 ms）。

**仍存在的局限（如实记录）**
- **seed 只有 3 条**：能精确断言、能覆盖 4 种数据形态，但验不了多页翻页与百条级分页边界 → 更优做法是加一个 100–300 条的 golden 数据集（脱敏/合成），分 marker 跑。
- **真实规模验证不是 nightly**：目前是单次实测，数据更新后不会自动回归 → 应做成 nightly job 或发布前 checklist。
- **没有性能门禁**：`/api/stats` 720 ms 只是测过，未设基线阈值拦截回归。
- **云端仍是 mock**：真实云端（含鉴权/限流）未接入；瓦片失败只覆盖部分场景。
- **E2E 只跑 Chromium**：未覆盖多浏览器与移动端分辨率，也未覆盖需要真实文件的下载链路。
- 分类维度的数据模型仍是单值（D23 未修，属产品决策）。

### 云端依赖（mock 覆盖，2026-11-14）

SUT 有 4 个路由依赖外部对象存储。SUT 是**独立子进程**，测试进程内的 requests-mock 拦不到它，
因此给 SUT 增加 `GUOHUA_CLOUD_BASE` 入口（第 5 处可测性改造，瓦片地址也统一走它），
测试时指向 `tools/fake_cloud.py` 本地假云端，用 `/__mode` 切换分支：

| 分支 | 覆盖内容 |
|---|---|
| 成功 | 缩略图、静态图片、cloud_url、**长卷瓦片拼接（2x1 → 1024x512）** |
| 业务失败 404 | 图片不存在 → 404（语义正确）|
| 基础设施失败 500 | 应 5xx/明确错误 → 现为 **D19**（伪装 404）|

## 性能基线（tools/bench.py）

轻量压测（不用 Locust，线程池并发打本地 SUT），`GET /api/images?per_page=50`：

| 并发 | 请求数 | 成功率 | P50 | P95 | RPS |
|---|---|---|---|---|---|
| 1 | 50 | 100% | 8.3 ms | 24.1 ms | 101 |
| 10 | 100 | 100% | 34.5 ms | 38.2 ms | 29.5 |
| 20 | 200 | 100% | 87.6 ms | 95.4 ms | 12.2 |

**结论（可讲的分析）**：服务端单请求约 8 ms；并发升高后**吞吐反而下降**（101 → 29.5 → 12.2 RPS），
说明瓶颈先在**压测客户端**（单进程线程池 + 每请求新建连接 + GIL），而不是服务端。
要压出服务端真实上限，需要多进程压测工具（Locust）或把连接池复用起来。
